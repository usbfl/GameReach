# v0.8.1 查询问题修复与验证

日期：2026-10-21。目标仍然是准确理解兴趣、高效寻找有充分依据的真实游戏。

## 先说明结论

四种原句都在真实测试中得到过通过准入的卡片。第一条首轮没有推荐，保持条件继续调查后得到1张；续查后段遭代理阻断，任务如实保留为部分完成，已完成的卡片没有丢失。其余三条在各自单次预算内完整结束并各得到1张。

这不表示已经证明推荐符合用户所有隐含想法，也不保证每次模型输出相同。测试用隔离数据库，没有导入私人游戏库，因此可能返回用户已玩过的游戏；以下游戏名是链路验收结果，不是最终个性化推荐名单。

当前目录的原数据库没有用户所列四条历史 live 任务，所以不能逐条还原那四次运行日志。本轮复测原句并定位可复现的代码问题，没有改写历史报告、原始配置或个人资料。

## 复现的原因与修正

| 问题 | 证据 / 影响 | 修正 |
|---|---|---|
| 规划协议失败 | 第一条原句在v0.8召回20款后，以 invalid_model_protocol 停止，尚未读取评论；不是实际找到20款不适合的游戏 | 已识别条件的必要取数动作由程序直接安排；需要模型决策或人工接管的流程仍保留，且明确记录哪些步骤没有调用模型 |
| 模型 Schema 与后端类型不一致 | value/target 原先允许任意 JSON，后端却要求0–4整数、布尔或枚举；会把整批响应拒绝 | 按机制写入类型约束，缩减角色无关字段；一次格式修订给出错误路径；仍有个别坏字段时仅保留格式有效的候选，随后照常独立核验 |
| 偏好被漏读或读反 | “动作之外有构筑”漏掉动作节奏；“跑图简单”原先成为高跑图惩罚；“死亡惩罚低”无独立维度 | 新增死亡损失、寻路负担；区分死亡后重走和捡尸；分开处理同句各机制的褒贬方向，避免“少刷”影响“重技巧” |
| 参考作误变类型限制 | 长段落内的 DARK SOULS 被直接变成 soulslike 搜索条件 | 类型线索忽略《书名号》内参考作；不继承其未明确表达的常见机制 |
| 召回过宽或单一 | 仅RPG/砍杀类型不足以定位动作构筑；流行肉鸽可能占满少量调查名额 | 补充受控动作RPG关键词和拼写别名；在动作RPG、动作肉鸽之间交替，再兼顾所选商店/平台；这些仅作目录召回线索，不充当画像证据 |
| PC 文本条件丢失 | 默认“全部平台”的处理可能清掉用户输入中明确的PC要求；重排也可能清掉 | 保留显式PC要求到取数、硬筛选、冻结重排 |
| 核验量表使用过严或概念混淆 | 中等级操作被要求提供高等级才需要的严格时机；构筑被要求字面说“流派”；重复通关被当成必须刷装备 | 细化等级证据标准；一般反应、走位可以支持中等级，武器/技能/道具改变打法不必使用“流派”字样；刷取必须核对刷取对象和推进必要性，不能由重复开局或负面情绪直接推断 |
| 预算必然超支 | 默认最多调查5款，但25次外部请求也包含模型调用；120条分层采样还需要分页 | 调查前为完整采集、提取、核验和一次局部修订预留请求预算；现有配置通常先调查2款，明确披露范围，真正超时/错误仍为partial |
| 同样的候选反复卡住 | 同一条件下已读足评论却没查清的候选，重试仍可能占据前两个名额 | 新任务对近24小时、相同原句/条件/协议下的这类候选暂缓优先取数，先调查其余游戏；不将未查清当作“不适合”，不改变排序事实或推荐条件 |
| 零推荐误导和代理异常 | “没有匹配游戏”混淆了没查完、没查清和确实不符；ProxyError原先可能直接失败且无报告 | 区分无目录候选、证据未齐、预算耗尽、调用错误；列出没查清的具体条件；代理阻断生成报告并保留合格卡片，不换网络路线或回退模拟 |

“跑图简单”本版解释为寻路负担低，界面会注明。若用户指死亡后快速回Boss，请明确写“低跑图惩罚”；系统不会把两者混成一个数值。

## 真实验收记录

实际使用现有 live + live 配置、DeepSeek deepseek-flash、IGDB/Twitch、Steam商店和公开评论。每次新任务保持18次模型、25次外部请求、180秒活跃时间上限，没有提高单次预算。

| 原句 / 场景 | 状态 | 合格卡片 | 实际结果 |
|---|---|---:|---|
| 战斗技巧、构筑变化、不需要大量刷装备，首轮 | completed | 0 | Elden Ring、Hades仍缺少足以确认刷取要求的依据，未放进推荐 |
| 同一句、同条件，开始新一轮 | partial | 1 | Dark Souls III：120条采集、60条送读、7条不同内容评论引用、4项有效机制；后段遭代理阻断 |
| 动作之外还要有构筑层 | completed | 1 | Elden Ring：120条采集、61条送读、5条引用、4项有效机制 |
| 魂、多构筑、死亡惩罚低、跑图简单 | completed | 1 | Elden Ring：120条采集、61条送读、5条引用、5项有效机制 |
| 游戏库兴趣长段落 | completed | 1 | Hades：120条采集、62条送读、7条引用、5项有效机制 |

61/62是初始提取与局部修订实际送读的不同评论片段合计，不是每次超出60条上限。采集、送读、复用、引用仍分开计数。分层样本不能当作总体玩家好评率。

四个首轮测试都用了20次外部请求、8次模型调用，在约131–152秒活跃时间内结束。第一条续查用了13次外部请求、3次模型尝试，其中后段请求被代理阻断；执行工具也报告该阶段网络审批被取消。没有绕过限制。新一轮是另一个明确触发的任务，有独立消耗，不是把两轮伪装成一份预算。

最终推荐的逐字引文定位、HTTPS来源、本地同条件重排和矛盾硬条件检查通过；重排不调用模型或外部接口。HTTPS格式和逐字位置不证明人工语义正确率，也不证明全部链接实时可访问。没有另做全市场召回率或玩家满意度测试。

可复核的脱敏记录：`evaluations/live_verification_081.json`。其中新增的“缺失条件”说明是对保存快照的本地重放，名单已核对不变；没有把重放记作新的模型/网络调用。记录不包含所有开发排查调用，不能当作账户总账单。

## 如何使用新版本

1. 停止旧服务，备份数据库；解压到新目录，保留原来的 `.env` 和 `data/gamereach.db`，不要把旧源码覆盖回新版本。
2. 启动后确认版本为0.8.1，重新开始探索。旧任务是历史快照，不会自动重写成新结果。
3. 若资料充分但某条关键限制仍无法判断，结果页会说明具体未知项。可点击“保持当前条件，开始新一轮调查”；这会产生新的真实调用，不会提高单次上限或放宽条件。
4. 在入口原句、当前条件和平台范围相同时，已读足评论却仍只差条件判断的候选，会暂时让出取数名额。只读取历史记录，不引入额外模型、向量库或监控系统。

此次量表从2.0更新到2.1：操作、构筑和重复刷取需按新规则重核验；未改动的旧维度仍按其原量表版本检查。新增死亡损失和寻路负担，共18维。旧报告和原引文保留，旧量表快照需重新探索后才能按新规则重排。无需新增数据库表。

## 评论与预算设置

采样和准入默认值保持不变：

```dotenv
MAX_REVIEWS_PER_GAME=120
REVIEW_CONTEXT_LIMIT=60
MIN_REVIEWS_FOR_RECOMMENDATION=20
MIN_CITED_REVIEWS=3
MIN_KNOWN_MECHANICS=3
```

如需要扩大采样，可修改根目录 `.env` 的采集/送读上限，保存后重启，详见 CONNECTIONS.md。单纯提高采样上限会增加消耗，不保证查清罕见条件。

若希望每轮调查更多候选，可以自行提高请求、模型、时间预算；本轮没有替用户改动这些值。推荐门槛、必须条件和未知不通过的规则没有降低。程序不能保证每轮一定凑出某个推荐数量。
